EDI 837 → CMS response file generator

Automation I built · Veradigm

Test data stopped being something the team had to budget for.

✓generated· 837 in, response files out· format lives in templates
PlaywrightPythonJinja2EDI 837
Problem
Producing CMS response files from EDI 837 claim inputs was slow, manual and easy to get subtly wrong - and every QA cycle needed fresh ones.
Approach
Parse the 837 input, map segment and loop data to a response model, then render the file through Jinja2 templates so the format lives in one reviewable place. Driven with Python; Playwright handles the portal legs that have no API.
Outcome
Response-file generation time dropped sharply and the team stopped waiting on hand-built fixtures.
Why it matters
Templating the format meant a CMS spec change became a template edit, not a re-scripting exercise.

My Selenium BDD automation framework

Architecture sample · one shared driver

One framework, reused across projects - not a script rewritten each time.

Runner→feature→ StepDef→Page→Base ·✓single WebDriver
Java SeleniumCucumberPOMJUnitMavenPageFactory

The same layered structure runs three of my public projects unchanged - a JuiceShop suite, a nopCommerce task and a data-collection tool. Swap the feature files and the page objects; the framework underneath doesn't move.

Execution flow Runner to assertion

1 · Runner

Runner.java is annotated @RunWith(Cucumber.class) with @CucumberOptions pointing features at src/test/features and glue at the step-def package. It emits pretty, HTML, JSON and JUnit XML reports in one run. An @AfterClass teardown quits the browser exactly once.

2 · Gherkin feature

Plain-language scenarios a non-tester can read and approve:

Given browser is open
Then go to the login page
When user enters "<email>" and "<password>"
And click on login button
Then user is navigated to the home page

Data comes in as {string} parameters, so one scenario covers many datasets.

3 · Step definitions

Every *StepDef class extends ParentScenario. Steps stay one line - they delegate straight to a page object and hold no selectors and no waits of their own. That's what keeps them readable.

4 · ParentScenario

Extends ParentDriver, calls getDriver() once, and constructs every page object as a public field. Because each step-def inherits from it, they all share the same driver and the same page instances - no re-instantiation, no second browser.

5 · ParentDriver - the shared driver

Holds a static WebDriver behind a lazy guard: if (driver == null) build it, otherwise hand back the existing one. Detects the host OS and configures ChromeOptions per platform (--start-maximized, --remote-allow-origins=*, 20s implicit wait). One browser for the whole suite, created on first use and quit by the Runner.

6 · Page Object Model

BasePage takes the driver, runs PageFactory.initElements, and owns the shared WebDriverWait (30s) plus an Actions instance. Every page extends it, so LoginPage inherits the waits and helpers and only declares its own @FindBy elements and behaviour methods.

7 · Constants

All URLs and XPaths are public static final String in one file, referenced as @FindBy(xpath = Constants.LOGIN_BUTTON). A UI change is a one-line edit in one file, never a hunt through step definitions.

Why it's built this way

The layering exists so each concern has exactly one home: Gherkin owns intent, step defs own translation, pages own interaction, Constants owns selectors, ParentDriver owns lifecycle. That's what makes the framework portable between projects instead of disposable.

Case study Profile photo upload - consumer fintech platform

Coverage designed

  • Format matrix - JPEG, PNG with alpha, WebP, HEIC from iOS, animated GIF, BMP, TIFF, SVG, CMYK colour profile, 16-bit HDR, progressive JPEG, grayscale
  • Geometry - 8K DSLR at 6000x4000, 50x50 micro icon, 5:1 panorama, 1:5 tower, EXIF orientation tags 3 and 6
  • Crop modal UI - zoom slider at both extremes, pan boundary detection, live thumbnail sync, Cancel discards, Save previews
  • Negative - .pdf and .mp4 rejection, 0-byte file, corrupt header behind a valid extension, 45MB oversize, cancelled OS dialog
  • Security - XSS payload in the filename, script-bearing SVG, EXIF GPS coordinate stripping before CDN delivery
  • Resilience - Slow 3G throttling, mid-upload network loss, rapid double-click race condition, 625MP decompression bomb
  • Compatibility - Chrome, Firefox, Safari, Edge, plus a 375x812 mobile viewport

What it found

  • Blocker - saving the profile section returned a failure toast and left the button stuck disabled; changes reverted on refresh. Reproduced across all four browsers, which pointed at the API rather than the front end.
  • Medium - a 45MB upload froze the tab for 8 seconds, then failed with a generic message that never stated the size limit.
  • Medium - going offline mid-save failed silently, with no offline warning at all.
  • Low - upload spinner showed no percentage progress on a slow connection; an 18-second wait looked like a hang.
  • Held up - filename XSS was sanitised, SVG upload was rejected, EXIF orientation auto-corrected, and double-click was debounced.

Requirement clarification log

Three open questions raised back to the team rather than guessed at - the exact min/max file size rule, the official policy on HEIC, TIFF and animated GIF, and whether EXIF stripping is server-side. Each logged with impact, risk and a recommendation. Ambiguity in a spec is a defect in the spec.

Traceability

25 named test assets mapped 1:1 to case numbers, and a screenshot evidence log cross-referencing every case that depends on it. A reviewer can go from a result straight to the artefact that produced it.

Client name withheld and defects described without endpoint detail. The downloadable template is the reusable format, with a generic login example filled in.

S2 · High P1 DEFECT-4821 · Claims Intake → 837P Validation

Title

837P claim with valid secondary-payer COB segment is rejected as CO-22 instead of routing to coordination of benefits

Test environment

QA2 · build 24.8.3 · MS SQL Server 2017 · Chrome 127 on Windows 11 · submitter profile PRO-837P · first seen build 24.8.1

Summary

An 837P claim carrying a valid secondary-payer COB segment is rejected with CMS CO-22 instead of being accepted for coordination of benefits.

Pre-conditions

  1. Member enrolled in a Medicare Advantage plan with an active secondary payer on file.
  2. Submitter configured for 837P professional claims.

Steps to reproduce

  1. Submit an 837P with loop 2320, SBR01 = 'S', and a populated AMT*D segment.
  2. Poll the DTS response queue until the 277CA is generated.
  3. Open the 277CA and inspect STC01-2.

Expected

Claim accepted (STC01-2 = A2), routed to COB processing, secondary payer amount retained.

Actual

Rejected with CO-22 - "care may be covered by another payer". The AMT*D value is dropped before payer-order resolution runs.

Attachments

  • Screenshots - annotated 277CA response showing the rejection code
  • Screen recording - full submit-to-response cycle, 40s
  • Logs - intake service log slice around the correlation id
  • Payload - the exact 837P used, plus the returned 277CA
  • Query output - SELECT ClaimId, PayerSeq, CobAmount FROM stg.ClaimPayer WHERE ClaimId = @id → CobAmount is NULL

Analysis

Loop 2320 parses fine, but stg.ClaimPayer is written before the COB amount is mapped - so payer-order resolution reads a NULL and falls through to the primary-only branch.

Regression risk

Any 837P or 837I with more than one payer. Recommend promoting this case into the smoke set.

Risk-based test strategy

ISTQB CTFL v4.0 applied

I don't test everything equally. Coverage follows risk.

rank by risk→cheapest layer→ written exit criteria→automate the stable core
Risk matrixBoundary & EPExit criteriaTraceability

Likelihood of failure times cost of that failure - so scarce time lands where it changes the release decision.

1 · Risk ranking
Score each area on failure likelihood and business impact. In claims, money and compliance paths outrank cosmetics every sprint.
2 · Layer selection
Push each check to the cheapest layer that can catch it - API and database assertions over UI clicks wherever the UI isn't the thing under test.
3 · Entry / exit criteria
Written before execution starts, so "are we done?" is answered by the criteria and not by the calendar.
4 · Regression selection
Automate the stable high-risk core; keep exploratory time for what changed. Every escaped defect earns a permanent regression case.
